## 幻灯片 1-1｜封面

**面向算法开发的 AI Loop 基础设施**

*NetTrainBridge — 让「改代码 → 训练 → 验证 → 分析 → 再改」转起来*

- 为具身智能算法研发提供**可重复、可追溯、可自动化**的迭代闭环底座
- 打通 Gradmotion 云端训练 ↔ 公司 Isaac / sim2sim 验证 ↔ 家里一条命令监控
- **Loop 关键词**：缩短单次迭代周期、降低 Loop 断点处的人工摩擦

---

## 幻灯片 1-2｜痛点：Loop 缺了「仿真验证」反馈通道

### 背景：训练侧 Loop 已在转

算法同学已能根据 **gm 训练日志** 完成多轮「训 → 看 → 改 → 再训」：

```text
改代码 → gm 训练 → 盯训练日志 → 分析指标 → 调参/改奖励 → 再训练 → …
         └────────── 当前在转的「训练内 Loop」──────────┘
```

**典型决策依据**（如 `Learning iteration 5999/6000`）：


| 类别          | 常看指标                                                      | 怎么用             |
| ----------- | --------------------------------------------------------- | --------------- |
| **收敛 & 稳定** | Value / Surrogate / State estimator loss                  | 判断有没有训崩、要不要降 lr |
| **整体效果**    | Mean reward、Mean episode length                           | 粗看策略有没有变好       |
| **分项奖励**    | `rew_tracking_lin_vel`、`rew_orientation`、`rew_foot_slip`… | 定位奖励设计问题，指导改权重  |
| **效率**      | Computation steps/s、Iteration time                        | 看训练效率、资源占用      |


---

### 痛点：缺第二条反馈通道——仿真验证（含 MuJoCo sim2sim）

**训练日志里的 Mean reward ≠ 目标仿真环境里的真实表现。**

仿真验证不是单步「跑一下 play」，而是**两层环境验收**：


| 验证层级                | 环境                     | 目的                      | 当前状态                |
| ------------------- | ---------------------- | ----------------------- | ------------------- |
| **L1：策略 rollout**   | Isaac Gym（`play.py`）   | 看训练出的策略在 Isaac 里站得住、走得稳 | 需人工到公司训练机执行         |
| **L2：环境迁移 sim2sim** | Isaac Gym → **MuJoCo** | 验证策略跨仿真器是否仍有效，更接近下游部署链  | 同样人工串联，**未纳入 Loop** |



| Loop 反馈通道      | 现状                                   | 局限                                           |
| -------------- | ------------------------------------ | -------------------------------------------- |
| **训练侧反馈**（已有）  | gm 日志：loss、Mean reward、各 `rew_`* 分项  | ✅ 训练内快速迭代；⚠️ 只反映训练环境内 rollout                |
| **仿真验证反馈**（缺失） | Isaac `play.py` + **MuJoCo sim2sim** | ❌ 两层验证都靠人工，单次 1～2 小时；Isaac 与 MuJoCo 结论散落、难对照 |


**典型误判**：

- 日志 `Mean reward: 163.85`、`rew_tracking_lin_vel: 0.57` 不错 → **以为可收工**
- Isaac rollout 站不稳、打滑 → **训练指标与仿真表现脱节**
- 即使 Isaac 过关，**MuJoCo sim2sim 未跑** → 环境迁移风险未知
- 补验需**跳出 Loop**，人工登录训练机、拼路径、分步跑 Isaac 与 MuJoCo，结论**接不回**下一轮决策

#### 流程对比：仿真验证环节

```text
【改造前 — 仿真端人工接力（未纳入 Loop）】

  gm 训练完成
       │
       ▼
  ┌─ 人工登录公司训练机 ─────────────────────────────────────┐
  │  clone 代码 → 下载/放置 checkpoint → 对齐 load_run 路径   │
  └──────────────────────────┬───────────────────────────────┘
                             ▼
                    Isaac Gym：play.py rollout
                    （站不稳？打滑？需人盯）
                             │
                             ▼  另起一次手工
                    MuJoCo：sim2sim 迁移验证
                    （Isaac 与 MuJoCo 指标散落两处）
                             │
                             ▼
              人工拷贝 CSV / 日志 → 表格分析 → 勉强接回「再改代码」
              
  问题：两层验证断裂、耗人、难复现、与训练日志无法自动对照
```

```text
【改造后 — 仿真端接入 Loop（目标形态）】

  gm 训练完成（或 ntb 备训完成）
       │
       │  家里一条命令：ntb test run --watch
       ▼
  ┌─ 公司 Agent 无人值守执行 ─────────────────────────────────┐
  │  sync 代码 → 拉 checkpoint → 同窗目录布局                    │
  │       │                                                    │
  │       ▼                                                    │
  │  L1：Isaac Gym  play.py  rollout  → 指标上报 Server        │
  │       │                                                    │
  │       ▼                                                    │
  │  L2：MuJoCo sim2sim（Isaac → MuJoCo）→ summary / metrics   │
  │       （同一 job 档案，可与训练日志对照）                     │
  └──────────────────────────┬───────────────────────────────┘
                             ▼
              家里 ntb job / watch 查结论 → 分析 → 再改代码

  价值：Isaac + MuJoCo 两层验证串进同一条 Loop，全程可追溯
```

```text
【单通道 vs 双通道 — 总览】

  改造前：
    训练日志 Loop ✅ 自转          仿真验证（Isaac + MuJoCo）╳ 人工断裂

  改造后：
    训练日志 ──┐
               ├──▶ 分析 ──▶ 再改代码
    ntb test ──┘   （Agent 自动跑 Isaac → MuJoCo sim2sim）
```

**一句话**：Loop 能靠训练日志转，但**仿真端（Isaac + MuJoCo sim2sim）未接入**——验得慢、靠人肉、两层环境结论对不上训练侧。

## 幻灯片 1-3｜风险：Loop 的训练引擎单点依赖 Gradmotion

### 背景：训练引擎绑在外部平台上

当前「训练内 Loop」主引擎是 **gm 云端 GPU**。Gradmotion 作为外部平台存在**不可控风险**——服务故障、配额/策略调整、环境不兼容等，可能导致**未来不可用或无法按现状使用**。


| 维度               | 现状                                                                        | 对 Loop 的影响                                         |
| ---------------- | ------------------------------------------------------------------------- | -------------------------------------------------- |
| **主路径训练**        | `gm task create` + `run`（云端 GPU）                                          | ✅ 当前首选；⚠️ **单点依赖**，平台风险算法组无法自控                     |
| **备用训练路径**（已开发）  | 家里 `ntb train run` → Server 建任务 → **公司 Agent** 执行 `train_with_metrics.py` | ✅ gm 停摆时 Loop **仍可继续**；指标/日志/checkpoint 走同一 NTB 通道 |
| **与验证 Loop 的关系** | Agent 同时承担 train / sync / test                                            | 备训 checkpoint 可继续 `ntb test run`，**训练—验证双通道仍闭合**   |


```text
【训练双路径：主 + 备】

  主路径：改代码 ──▶ gm 云端训练 ──▶ 训练日志 ──▶ 调参 …
                          │
                    平台不可控风险 ⚠️

  备路径：改代码 ──▶ ntb train run ──▶ Agent（公司 GPU）训练 ──▶ ntb watch …
                          │
                    train_source=ntb，同一 Server 存档
```

> **设计原则**（README）：训练**首选 gm**；gm 不可用时 `**ntb train run`** 兜底——给 Loop 一条**可切换的备用训练引擎**，而非推倒重来。

**一句话**：训练侧也单点绑 gm——已用 **Agent 兜底训练** 降低不可控风险，保证 Loop 在平台波动时仍能转。

## 幻灯片 1-4｜我们是什么：AI Loop 基础设施（定位）

NetTrainBridge **直接回应前文两大问题**：


| 前文             | 问题                               | 本基础设施的应对        |
| -------------- | -------------------------------- | --------------- |
| **幻灯片 1-2 痛点** | Loop 缺仿真验证通道（Isaac + MuJoCo 靠人工） | → **① 训验打通**    |
| **幻灯片 1-3 风险** | 训练引擎单点依赖 gm 外部平台                 | → **③ 私有化部署基础** |
| **两者之上**       | 缺可复用的 Loop 底座，难支撑更复杂算法           | → **② 路径延伸**    |


### 三点定位（各对一条痛点 / 风险）

**① 打通 gm 训练与本地仿真验证 — 针对痛点 1-2「仿真端未纳入 Loop」**

- **回应什么**：训练日志 Loop 已在转，但 Isaac / MuJoCo **两层验证靠人肉**，结论散落、接不回下一轮  
- **做什么**：`gm` 训完 → 家里 `ntb test run` → 公司 Agent **无人值守**跑 play + sim2sim → 结果回传 Server  
- **效果**：训完**直接获得测试结果**，无需人工登录训练机、拼路径、分步跑验证；训练指标与仿真指标进**同一 job 档案**

**② 打通路径 — 为后续大脑算法开发做好准备**

- **回应什么**：痛点不止于「少跑几次 play」——缺的是**可复用、可扩展的 Loop 底座**  
- **做什么**：在云 Server 队列 + Agent 执行 + `ntb` 命令之上，已跑通 **训练 → 验证 → 存档 → 分析** 小闭环  
- **效果**：运动控制 / sim2sim 先验证基础设施；后续大脑、决策类算法**复用同一套队列与执行面**，不必从零搭流水线

**③ 为未来私有化服务器部署打好基础 — 针对风险 1-3「gm 单点依赖」**

- **回应什么**：训练主引擎绑在 Gradmotion 云端，平台故障 / 策略变化时 Loop 可能停摆  
- **做什么**：已落地 **自有云 Server**（任务调度、指标、产物）+ **公司训练机 Agent**（train / test 执行）；`ntb train run` 备训与 `ntb test` 验走**同一私有链路**  
- **效果**：gm 仍是当前首选，但 Loop **不再等于 gm**——私有化服务器上可逐步承接训练与验证，为**自建 GPU 集群、完全内网部署**铺好架构，降低对外部平台的硬依赖

```text
  痛点 1-2                    风险 1-3
  仿真未接入 Loop      →①←   gm 单点依赖
       │                          │
       └──── AI Loop 基础设施 ────┘
                    │
              ② 路径延伸至大脑算法
              ③ 私有化 Server + Agent 已就位
```


| 定位点         | 针对        | 今天已有什么                                   |
| ----------- | --------- | ---------------------------------------- |
| **① 训验打通**  | 痛点 1-2    | `ntb test run` + Agent 自动 Isaac / MuJoCo |
| **② 路径延伸**  | 缺 Loop 底座 | Server 队列、`ntb` 命令、Skill 可编排             |
| **③ 私有化基础** | 风险 1-3    | 云 Server + 公司 Agent；`ntb train` 备训       |


**一句话**：**补上仿真通道、铺好延伸路径、自有服务器架构就位** — 分别接住前文的痛点与风险。

## 幻灯片 1-7｜效果量化：Agent 无人值守自动 Loop

> 核心变化：算法同学**触发一次**，公司训练机 **Agent 自动跑完**仿真验证 Loop，人无需守在 GPU 机器旁。

### 人工参与 vs Agent 自动执行


| 维度        | 改造前（人工仿真验证）                          | 改造后（Agent 自动 Loop）                                  |
| --------- | ------------------------------------ | --------------------------------------------------- |
| **谁干活**   | 人登录训练机，逐步执行                          | **Agent 7×24 轮询抢任务**，自动 clone / 拉模型 / 跑脚本 / 上报      |
| **人要做什么** | 全程在场：拼路径、启 play、等 MuJoCo sim2sim、拷结果 | **一条命令** `ntb test run`（可选 `--watch` 在家里看进度）        |
| **仿真链路**  | Isaac、MuJoCo **分两次人工**跑              | Agent **串行执行** Isaac rollout → MuJoCo sim2sim（目标形态） |
| **等待方式**  | 人盯着终端，≈9 min 也不能走开                   | 机器自动跑 ≈9 min+，人可并行做别的                               |
| **结果回流**  | 本地 CSV/日志，人工整理                       | 自动 `POST` 指标、日志、test 产物 → Server → `ntb job` 可查     |


### Agent 自动 Loop 在做什么（无人值守）

```text
  家里：ntb test run --watch          ← 人只触发 + 可选围观
              │
              ▼
  Server：创建 test job（PENDING）
              │
              ▼
  Agent（公司 GPU，后台常驻）：
    claim → sync 代码 → FETCH checkpoint
         → Isaac play.py rollout
         → MuJoCo sim2sim
         → 上传 metrics / summary.json / checkpoint
         → COMPLETED
              │
              ▼
  家里：ntb job <id> 看结论           ← 人回来做算法决策
```

### 对算法迭代的意义


| 项            | 效果                                 |
| ------------ | ---------------------------------- |
| **迭代转速**     | 仿真验证从「占 1～2 人时」→「触发后 Agent 自理」     |
| **Loop 连续性** | 训练完不必「明天再找机器验」— 当晚提交 test，次日看结果    |
| **可复现**      | 同一 `ntb test run` 参数可重复跑，不依赖某人是否在场 |
| **双通道决策**    | 训练日志（gm）+ 仿真指标（Agent 回传）共同支撑下一轮改代码 |

5. **阶段**：**MVP 试运行**，小组内验证中。
6. **受众**：具身智能**算法小组**，用于日常算法迭代。

# 第二部分：技术实现方案

> **说明**：本项目是 **AI Loop 基础设施**——先打通训练 / 验证 / 存档，再在其上提供稳定 `ntb` 命令供 Skill / MCP 编排。**不绑定大模型、不挑 Agent 框架**。

## 幻灯片 2-1｜运行环境

### 三端 + 一云

| 节点 | 环境 | 职责 | 网络 |
|:---|:---|:---|:---|
| **云 Server** | Linux `:8000` | 任务队列、SQLite、`data/{job_id}/` | 被动 HTTP；**不回连**训练机 |
| **公司训练服务器** | F1 + Isaac GPU | `agent.py` 抢任务，train / test / 上报 | **仅主动出站**（经代理轮询） |
| **家里开发机** | Win / Linux | `ntb` / `gm` CLI、git | HTTP 建任务、查结果 |
| **gm 云端** | 平台托管 | 主路径 GPU 训练 | 家里 `gm` CLI |

**网络原则**：公司侧**只能训练机找云**（轮询 → claim → 上报）；云 **╳→** 训练机；算法同事**不必登录**训练机。

```text
  gm 云端 ◀── gm CLI
  家里 ──HTTP──▶ 云 Server :8000 ◀── 训练机主动 HTTP+代理
                  队列 + data/
```

- 云 **纯 API** + CLI（见 2-5）；训练机**只出站、不开入站**

```text
  第一层：AI Loop 基础设施（本项目核心）
```

## 幻灯片 2-3｜模型：不挑模型，基础设施与策略解耦

我们是 **AI Loop 基础设施**，**不绑定**某一种策略网络、任务或训练平台——Loop 里用什么模型，由算法同学按实验决定，基础设施只负责**调度、执行、存档**。


| 维度           | 说明                                                                                |
| ------------ | --------------------------------------------------------------------------------- |
| **设计原则**     | **模型无关**：换 `task`、换网络结构、换 checkpoint 都不改 Server / Agent 核心逻辑                      |
| **Loop 交付物** | 各类 RL **策略 checkpoint**（如 `model_3000.pt`），非对话大模型                                 |
| **训练主路径**    | Gradmotion 云端 — 算法自选 `run_name`、超参、训练步数                                           |
| **训练备路径**    | `ntb train run` → 公司 Agent — 同一套指标/日志通道                                           |
| **验证**       | `ntb test run` — 按 `load_run` + `checkpoint` 加载**任意已训模型**做 Isaac / MuJoCo sim2sim |
| **可扩展**      | 新任务加 `train_command` / `test_command` 配置即可，无需 fork 基础设施                           |


```text
  各种 model_A.pt、model_B.pt、不同 task …
              │
              ▼
        NetTrainBridge（统一 Loop 管道）
              │
              ▼
  同一套：建任务 → Agent 执行 → 指标回传 → job 档案
```

**一句话**：基础设施回答「怎么转 Loop」；**用什么模型**是算法实验的事，我们**不挑、不锁**。

## 幻灯片 2-4｜Skill / 工具 / MCP：基础设施命令 → 可编排 Skill / MCP

### 核心逻辑：先打通，再编排

NetTrainBridge **先完成训练—验证基础设施**（Server + Agent + `ntb` CLI）。打通之后，家里出现一批**稳定、可脚本化的自动化命令**；这些命令是 Skill / MCP 的**原材料**——按需把命令链写成 Skill 或挂到 MCP，**不绑定某一种 IDE 或 Agent 产品**。

### A. 基础设施提供的自动化命令（`ntb`）

| ----------- | -------------------------------------------------- | -------------------- |
| **健康 / 任务** | `ntb health`、`ntb jobs`、`ntb job <id>`             | 查 Server、列任务、看详情     |

## 幻灯片 2-5｜UI 交互：CLI 风格，为 AI Loop 服务

**为什么用 CLI，不用 Web 大屏？** — AI Loop 要高频、可重复、可脚本化；**终端命令**最适合「触发一圈 Loop → 看结果 → 再触发」，也方便 Skill / MCP 逐条调用 `ntb` 子命令。


| 界面              | 形式              | 典型命令                                              | 在 Loop 中的作用    |
| --------------- | --------------- | ------------------------------------------------- | -------------- |
| **NTB**         | 终端 CLI          | `ntb test run --watch`、`ntb job <id>`、`ntb watch` | 触发验证、看仿真结论     |
| **gm**          | 终端 CLI          | `gm task logs --follow`                           | 主路径训练侧反馈       |
| **API**         | FastAPI `/docs` | HTTP + `--json`                                   | 脚本 / 自动化集成     |
| **Skill / MCP** | 编排层（可选）         | 把上表命令串成模式 A～E 或分析流                                | 降低记忆成本，**非必选** |


```text
  AI Loop 友好 = CLI 友好

  $ ntb test run --load-run ... --watch   # 触发一圈验证
  $ ntb job <id>                          # 读结论，决定下一轮改什么
  $ gm task logs --follow                 # 训练侧通道

  → 命令稳定 → 可写 Skill / MCP → Loop 转得更快
```

**一句话**：CLI 不是「简陋」，而是 **AI Loop 基础设施的标准交互面**；Web Dashboard 不是当前方向。

## 幻灯片 2-6｜智能体框架：基础设施不挑框架

Loop 分**两层**，编排层**不锁定**任何 Agent 产品或 IDE：


| 层级           | 是什么                                    | 做什么                         | 是否挑框架                           |
| ------------ | -------------------------------------- | --------------------------- | ------------------------------- |
| **基础设施（核心）** | Server + **NTB Agent** + `**ntb` CLI** | 训练 / sync / test 自动执行、指标存档  | **固定**，自研                       |
| **编排层（扩展）**  | Skill、MCP、或人工记命令                       | 把 `ntb` / `gm` 命令串成 Loop 流程 | **不挑** — 任意支持 Skill 或 MCP 的载体均可 |


```text
  编排层（可换、可选）
  ┌────────────────────────────────────┐
  │  Skill 文件  /  MCP Server  /  人 │
  │  读 cli/README 里的 ntb 命令        │
  │  串成：训练 → test → 分析 → 再改    │
  └─────────────────┬──────────────────┘
                    │ 调用 ntb / gm 命令
                    ▼
  基础设施层（本项目交付物）
  ┌────────────────────────────────────┐
  │  ntb CLI → Server → Agent          │
  │  无人值守跑 train / test / sim2sim │
  └────────────────────────────────────┘
```


| 对比  | 绑死某一 Agent 产品    | 本项目的分层                      |
| --- | ---------------- | --------------------------- |
| 编排  | 必须用某 IDE / 某对话框架 | **任意** Skill / MCP / 手工 CLI |
| 执行  | 依赖产品内置工具         | **统一**走 `ntb` + Agent       |
| 状态  | 聊天会话             | `job_id` + Server 任务档案      |


**一句话**：基础设施只管**把 Loop 跑通**；上面用 Skill、MCP 还是直接敲 `ntb`，**团队自选，不挑框架**。

## 幻灯片 2-7｜数据归一：训练 / 测试 / 分析统一上云 Server

> 改造前：训练在 gm、验证在训练机本地目录、分析 CSV 散落个人盘 —— **同一套训练代码的一圈 Loop，数据四处开花**。  
> 基础设施做法：**按 `job_id` 数据归一**，模型、测试产物、指标、元数据**统一归档到云 Server**，家里 `ntb job` 一处查看。

### 归一原则：一圈 Loop = 一个 `job_id` = 一份云档案

同一训练代码仓库、同一次 commit、同一 checkpoint 下的**训练结果、测试结果、分析结论**，都挂在同一个任务 ID 下，与 `repo_url` / `commit_sha` / `load_run` 在 `meta.json` 里对齐。

```text
  改造前（分散）                    改造后（归一）
  ──────────────                    ──────────────
  gm 云上的模型          ┐
  训练机 ~/job/ 日志     ├── 难对照    Server data/{job_id}/
  本地 isaac_diag CSV    ┘              ├── meta.json      （版本、来源、参数）
                                        ├── models/        （checkpoint）
                                        ├── test/          （sim2sim 产物）
                                        │   ├── summary.json
                                        │   └── metrics.jsonl
                                        └── （指标时序 → SQLite，按 job_id 关联）
```

### 云上存什么（按类型）


| 数据类型              | 存放位置                                             | 内容示例                                                             | 写入方                       |
| ----------------- | ------------------------------------------------ | ---------------------------------------------------------------- | ------------------------- |
| **任务元数据**         | Server `data/{job_id}/meta.json` + SQLite `jobs` | `commit_sha`、`gm_task_id`、`load_run`、`checkpoint`、`train_source` | 建任务 / Agent 结束时           |
| **训练指标**          | SQLite `metrics` 表（按 `job_id`）                   | loss、reward、step 时序                                              | Agent 训练过程中 `POST`        |
| **训练日志**          | Server 内存缓存（按 `job_id`）                          | 子进程 stdout，支持 `ntb logs -f`                                      | Agent 实时 `POST`           |
| **模型 checkpoint** | `data/{job_id}/models/`                          | `model_3000.pt` 等                                                | Agent 训练结束上传              |
| **测试结果**          | `data/{job_id}/test/`                            | `summary.json`、`metrics.jsonl`、videos/                           | Agent test / sim2sim 结束上传 |
| **分析输入**          | 可由 test 产物导出或同步归档                                | `isaac_diag_*.csv` 等仿真诊断数据                                       | 纳入 test 目录或关联同一 `job_id`  |


### 数据归一对 Loop 的意义


| 维度           | 改造前                      | 归一后                                     |
| ------------ | ------------------------ | --------------------------------------- |
| **训练 vs 仿真** | gm 日志一套、play 结果另一套       | 同一 `job_id` 下**训练指标 + test/summary** 对照 |
| **多人协作**     | 模型在谁机器、结论在哪目录靠人问         | `ntb jobs` / `ntb job <id>` **统一入口**    |
| **复现**       | 路径、commit、checkpoint 靠人记 | `meta.json` 锁定版本，同参数可重跑                 |
| **大脑算法延伸**   | 每种算法各搞一套存档               | **同一 Server 目录规范**，换 task 不改归档模型        |


### 与 Skill / 文档的分工


| 层级            | 放什么                             | 放哪                                     |
| ------------- | ------------------------------- | -------------------------------------- |
| **数据层（归一核心）** | 模型、测试、指标、meta                   | **云 Server** `data/{job_id}/` + SQLite |
| **编排层（可选）**   | Skill 提示词、`cli/README.md` 命令说明  | 训练仓库 git                               |
| **本地暂存**      | `record-run.json`（当次 Loop 参数草稿） | 本机 gitignore，最终结论以 Server 为准           |


```text
  数据流（归一）

  训练代码（GitHub）──commit_sha──▶ job 创建
         │
         ▼
  Agent 执行 train / test ──自动上报──▶ 云 Server
         │                              │
         │                              ├─ metrics / logs（过程）
         │                              ├─ models/（训练交付）
         │                              └─ test/（验证交付）
         ▼
  家里 ntb job <id>  ──一处读取──▶  分析（isaac-diag-eval 等）──▶ 下一轮改代码
```

**一句话**：**数据归一**是 AI Loop 基础设施的底座 —— 同一训练代码的一圈迭代，**产、测、析**全部落在云 Server 同一 `job_id` 下，不再散落训练机与个人目录。

## 幻灯片 3-2｜多人并行：私有化 Server 上的队列能力（已具备）

> 支撑 **① 训验打通**（多人同时提交 test）与 **③ 私有化基础**（自有 Server 作任务中枢，不依赖 gm 排队）。

基础设施按 **「多生产者 → 中央队列 → 消费者抢占」** 设计——这是私有化部署后小组并行的核心机制。

### 角色分工


| 角色      | 谁                             | 做什么                                              | 并行度                  |
| ------- | ----------------------------- | ------------------------------------------------ | -------------------- |
| **生产者** | 多名算法同学（家里）                    | 各自 `ntb train run` / `ntb test run` / `ntb sync` | **多人同时**提交           |
| **队列**  | **自有云 Server**（SQLite `jobs`） | `PENDING` 任务 FIFO 排队                             | **中央调度**             |
| **消费者** | 公司训练机 **Agent**（`agent_id`）   | 轮询、`claim` 抢占、执行                                 | 单 Agent 一单；**可多机扩展** |


```text
  同学 A ── ntb test run ──┐     （① 训完即提交验证，不必排队等人）
  同学 B ── ntb train run ─┼──▶  自有 Server 队列
  同学 C ── ntb test run ──┘              │
                                          ▼ claim
                               Agent 消费 → ③ 私有化链路上执行
```

### 队列与抢占（要点）


| 机制       | 说明                                                   |
| -------- | ---------------------------------------------------- |
| **入队**   | `ntb` → `POST /jobs` → `PENDING`                     |
| **顺序**   | `create_time ASC`（FIFO）                              |
| **抢占**   | `PUT /claim`，`WHERE status='PENDING'` 乐观锁；409 则换下一任务 |
| **隔离**   | 每任务 `job_id` + `data/{job_id}/`，多人互不覆盖               |
| **人机解耦** | 同学 `ntb watch` 自己的 job；Agent 无人值守消化队列                |


### 与三点定位的关系


| 定位          | 多人并行如何支撑                                      |
| ----------- | --------------------------------------------- |
| **① 训验打通**  | 多人训完后**同时** `ntb test run`，不必等「谁有空帮忙跑 play」   |
| **② 路径延伸**  | 队列 + Agent 与 `job_type` 无关，新算法只需加命令/配置        |
| **③ 私有化基础** | 队列跑在**自有 Server**，扩 Agent 即可扩消费力，**不绑 gm 配额** |


**规划扩展**：多 `agent_id` / 多 GPU 并行消费；`ntb jobs --status PENDING` 看排队深度。

| 阶段        | 目标                                            |

| **备训生产化** | `ntb train run` 稳定兜底，`train_source=ntb` 可日常切换 |
| **算力扩展**  | 多台训练机、多 `agent_id`，队列并行消费（见 3-2）              |

| **运维体系**  | Server 备份、`data/` 容量、Agent 监控与告警              |


```text
  ③ 私有化演进路径

  阶段 1（现在）  自有 Server + 单 Agent；gm 主训 + ntb 备训/验
```

## 附录：第一部分演讲备注（可选）

- **幻灯片 1-2 金句**：「训练日志能指导调参，但指导不了 Isaac 里站不站得住。」
- **幻灯片 1-3 金句**：「gm 是首选引擎，不是唯一引擎——Agent 备训让 Loop 不怕平台波动。」
- **与 gm 的关系**：gm = 主训练引擎 + 训练侧反馈；NetTrainBridge = 仿真验证通道 + Agent 备训 + 任务档案。
- **若被问「和 CI/CD 有何不同」**：CI/CD 面向代码合并；AI Loop 面向**模型迭代**——每次 Loop 的交付物是 checkpoint + 仿真指标，而不只是 build 绿/红。
- 效果数据：test ≈ 9 min 来自 R1-3；人工 1～2h 为组内典型 Loop 断点经验值；推广后建议统计「周 Loop 圈数 × 单圈节省」。
